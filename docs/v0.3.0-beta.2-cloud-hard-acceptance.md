## 2. 冻结行为与验收范围

beta.2 冻结以下 production 行为：

1. `SessionStart` 在 `startup|resume|clear|compact` 上进入 managed adapter；
2. `UserPromptSubmit` 进入同一个 managed adapter；
3. 两个事件都自动发出 `PWF_GLOBAL_HOOK_CANARY_V1`；
4. owned-plan 是 canonical plan 选择和 planning context 的唯一生产权威；
5. `SessionStart` 先组合 owned catch-up，再组合已验证的 planning context；
6. `UserPromptSubmit` 只组合 canary 与 planning context，不运行 catch-up；
7. plan child 失败时输出 canary-only，不允许 adapter 回退读取项目 planning 文件；
8. catch-up child 失败不能抑制已经验证的 canary 或 planning context；
9. snapshot、child output、timeout、进程组和安装 inventory 保持有界；
10. lifecycle Hook 保持只读，不修改项目 planning 文件。

本 runbook 不在 live `/opt/codex` 中制造破坏性 drift。no-plan、opt-out、detached session、非法路径、
损坏 transcript、child timeout、跨用户权限和 repair/fail-closed 矩阵由完整 Linux suite 覆盖。

## 3. 验收顺序与停止条件

严格按以下顺序执行：

1. Fresh Cloud exact-byte seal；
2. GitHub Release 两资产下载复核；
3. setup task 安装与 doctor；
4. 完全不同的新 task 执行 B；
5. 在该 task 中执行 C、D、E1；
6. Resume 同一个 task 执行 E2；
7. 保存 E2 原始 no-tools 回复后执行 F。

停止条件：

- 资产 SHA、版本、ZIP inventory 或 bootstrap external 任一失败：停止，不安装；
- setup/doctor 失败：停止，不进入 lifecycle 黑盒；
- B 的任一必需 canary 缺失或 source 不是 `startup`：保存原始回复后停止；
- C 没有真实 successful `apply_patch` / structured `patch_apply_end`：不得进入 D/E；
- D/E/F 任一严格门槛失败：保存原始证据，停止并诊断；
- 任一失败都不得通过修改已发布 beta.2 资产“原地修复”。

## 13. 后续新仓库提取边界

以 beta.2 建立精简新仓库是合理的长期治理方向，但属于独立迁移项目，不属于本次验收，也不自动
获得 Phase 4 授权。迁移前必须先建立 Discovery Gate，至少冻结：

- 新仓库必须保留的 production runtime、installer、contracts、manifest、tests、Release builder、
  bootstrap 和本 runbook；
- 哪些历史 evidence、旧 patch、旧版本文档只留在归档仓库；
- beta.2 golden behavior、69/69 Linux gate、双资产 SHA 和 rollback 语义如何转移；
- Git executable mode、LF attributes、license/provenance 和 exact allowlist 如何不丢失；
- 新仓库第一次 commit、第一次 Release 和 Cloud A～F 如何证明不是“复制后看起来能跑”，而是
  与 beta.2 冻结基线行为等价。

在该 gate 完成前，不从当前仓库删除历史文件，也不把当前仓库原地瘦身为新仓库。
